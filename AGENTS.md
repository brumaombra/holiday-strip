# Agent instructions

For AI agents (Claude Code, Codex, Copilot and others) working on this repository. `CLAUDE.md` imports this file, so every agent reads the same rules.

## What this project is

Holiday Strip turns a 72x12 truck LED matrix (864 WS2812B-compatible LEDs) into an animated holiday display, on an ESP32 DevKit (ESP-WROOM-32).

- `microcontroller/` is the PlatformIO firmware: the scenes of each holiday, the player that rotates and crossfades them, the LED output with its power limiter, the settings, and the HTTP server with the dashboard's API. The Wi-Fi setup and the device API come from [gizmo-common](https://github.com/open-gizmo/gizmo-common).
- `webapp/` is the Nuxt 4 dashboard, embedded in the firmware: the Strip, Device and WiFi tabs. It extends the gizmo-common web layer, and the mock device in `webapp/server/` answers like the firmware during development.

## Structure

- `src/main.cpp`: the entry point; loads the settings, starts the Wi-Fi and the server, and asks the player for a frame every 33 ms.
- `src/scenes`: one file per scene, the shared effects (`effects.h`), and the holidays with their scenes (`scenes.cpp`). A new scene goes at the end of its holiday's list, so the scenes saved before keep their place.
- `src/player`: follows the holiday (chosen, or picked by the calendar), rotates its scenes, crossfades between them.
- `src/calendar`, `src/settings/settings_rules.*`, `src/settings/settings_json.*`, `src/display/led_output.*`: the hardware-free logic (holiday of the date, countdowns, the rules and JSON of the settings, the LED mapping and power limiter).
- `src/settings`: the settings saved in NVS, shared between the loop and the web server.
- `src/server`: the dashboard's API (`/api/state`, `/api/settings`, `/api/frame`) and the embedded web app.
- `src/config`: pins, timings, power figures, defaults, languages.
- `src/webui`: generated by `npm run build:embedded`, never edited by hand.
- `tools/scene_video`: renders any scene to an MP4 with the real scene code; `tools/banner`: draws the README banner.

## Working rules

1. Keep the split between firmware and web app clear: no device logic in the web app, no front-end behavior in the firmware.
2. Keep the module boundaries of `microcontroller/src/`: extend the right module instead of adding logic to `main.cpp`.
3. Keep the hardware-free logic free of hardware headers, and test it with `pio test -e native`.
4. When a route, payload or validation rule changes, update the firmware handlers, the mock device in `webapp/server/` and the web app together.
5. Never change the NVS keys, the pins or the partition table without asking: they affect the boards and the data already saved on them. New keys are added, old ones keep their meaning.
6. Prefer small, hardware-aware changes: no blocking calls, no big buffers on the stack, no needless allocations.
7. Use the ui-vintage components as they are, never overriding them.

## With every change

1. **Write the changelog.** When someone using the strip would notice the change (a scene, the dashboard, the hardware or wiring, the setup steps, a fix), add a line under `## Unreleased` in [CHANGELOG.md](CHANGELOG.md), in the same commit. Write it for the people who flash and use the strip, not as a commit message: what changed for them, and what they need to do (flash again, rewire, set something up again). Internal changes (refactoring, tests, CI) need no line unless they change what the strip does.
2. **Keep the docs in sync.** Update the README when what it says changes, and the banner (`tools/banner/make_banner.sh`) when the look does.
3. **Check it before calling it done.** Run the tests (`pio test -e native` in `microcontroller/`, `npm test` in `webapp/`) and the release build (`npm run build:embedded` in `webapp/`, then `pio run -e release`).

## Releasing

Follow "Releasing" in the README. The version's notes must be moved from `## Unreleased` to a `## vX.Y.Z - YYYY-MM-DD` heading in CHANGELOG.md: they become the GitHub release notes, and the release workflow stops before building anything when they are missing or when notes are left under Unreleased.

Work on the `feature` branch; changes reach `develop` and then `main` one step at a time, only for a release.
